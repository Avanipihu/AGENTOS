1. Introduction — Integration, Visual Evaluation, and Research Framing

1.1 Contemporary Setting: The Omarchy Case Context

In modern software engineering, developers increasingly employ autonomous AI coding agents to edit files, execute test suites, and coordinate multi-step workflows. To ground our operating systems study in real-world practices, this investigation examines Omarchy [O1–O4], an Arch-based Linux desktop distribution explicitly tailored for workflows with AI coding agents:

  • Desktop Infrastructure [O1]: Combines Arch Linux with the Hyprland tiling Wayland compositor and Quickshell desktop widgets, creating an agile, scriptable workstation.
  • Agent Integration [O2]: Features built-in launchers for multiple coding agents, default agent configuration hooks, and an Omarchy skill enabling agents to query desktop commands and window states.
  • CLI and User Dotfiles [O3, O4]: Exposes workspace management through the omarchy command-line utility and organizes configuration into modular user dotfiles.

While Omarchy demonstrates how developers interact with coding agents in a modern Linux desktop, it operates under standard single-user Linux semantics. It does not introduce specialized kernel memory managers for agents or enforce fine-grained per-role file isolation. This motivates the need for our bounded, principled pedagogical model.

1.2 Research Question & Two-Layer Methodology

Core Research Question: How do conventional operating systems principles regarding limited physical memory and organized, protected file systems help analyze a hypothetical multi-agent workspace, and what do reproducible simulations demonstrate about those mechanisms?

To answer this question rigorously, the evaluation is structured around two complementary layers:

  1. Documentary Case Analysis: Extracting observable architectural decisions and resource boundaries from Omarchy's official documentation [O1–O4].
  2. Bounded Pedagogical Simulation (AgentOS): Implementing deterministic software simulations modeling three cooperative roles (Research, Coding, and Report) sharing m = 3 physical memory frames and a protected file directory hierarchy.

2. Problem Statement & Scope — Integration Perspective

Evaluating virtual memory and file systems in multi-agent environments presents four interconnected systems challenges:

  1. Paging Divergence: Two replacement policies receiving identical reference strings diverge in frame residency upon a single recency refresh, leading to completely separate downstream eviction paths.
  2. Allocation Anomalies (Belady's Anomaly): Expanding physical frame allocation is conventionally assumed to monotonically reduce or preserve page fault rates. Member 3 must visually prove that FIFO violates this assumption on specific workloads, whereas LRU guarantees monotonic improvement.
  3. Protection Boundaries & Information Leakage: In multi-tenant workspaces, authorization must be validated prior to node existence resolution. If an unauthorized agent attempts an access, it must be denied without revealing whether the target path exists.
  4. Lost-Update Prevention: When agents concurrently read, compute, and write shared deliverables, optimistic concurrency control must detect stale version overwrites.

3. Theoretical Background & Related Work

3.1 Demand Paging, Stack Algorithms, and Belady's Anomaly

In demand-paged virtual memory, logical address space is divided into equal-sized pages, and physical memory is partitioned into frames [C1]. A reference to an absent page generates a page fault trap:

  • Page Hit vs. TLB Hit: In hardware architectures, a Translation Lookaside Buffer (TLB) caches virtual-to-physical address mappings. A TLB hit speeds up hardware translation. In AgentOS, our metric is page residency: a page hit indicates that the requested abstract page identifier is currently resident in one of the 3 simulated physical frames.
  • Stack Algorithms: An algorithm is a stack algorithm if the set of pages resident in an m-frame configuration at time t is strictly a subset of the pages resident in an (m+1)-frame configuration: M(m, t) ⊆ M(m+1, t).
  • Least Recently Used (LRU): Because LRU always maintains the m most recently referenced unique pages, expanding capacity to m+1 merely appends the (m+1)-th most recently referenced page without altering the residency of the top m pages. Therefore, LRU satisfies the inclusion property and is mathematically immune to Belady's Anomaly (Faults(m+1) ≤ Faults(m)).
  • First-In, First-Out (FIFO): FIFO evicts the page loaded earliest, completely uncoupling victim selection from recency. Because arrival order does not satisfy inclusion, expanding capacity can cause FIFO to retain useless pages while evicting immediately required pages, producing Belady's Anomaly (Faults(m+1) > Faults(m)).

3.2 Hierarchical File Systems & Longest-Prefix Access Control

In hierarchical file systems, directory trees are organized from root /. Access permissions map agents (subjects) to path prefixes (objects) across privileges {r, w, c, d} (read/list, write/overwrite, create/mkdir, delete):

  • Longest-Prefix Matching: When agent S requests operation O on path P, the effective permission is resolved by finding the longest matching rule prefix. More specific child directory rules strictly override broader parent permissions.
  • Security Check Before Existence: Verifying authorization prior to path resolution ensures zero information leakage, preventing unauthorized agents from probing directory contents or mapping workspace structure.
  • Optimistic Concurrency Control: Files maintain a monotonic version counter incremented on each successful write. Writes specifying an expected_version mismatch trigger an immediate CONFLICT status.

Limitations

  1. Simplified Demand Paging: The simulation omits dirty-page writebacks, disk seek latency, TLBs, and hardware MMU translation.
  2. Abstract Page References: Page identifiers represent context tokens rather than physical memory pages.
  3. In-Memory File Nodes: Files exist as Python objects; physical disk fragmentation and journaling recovery are omitted.

8.2 Viva Voce Defense Preparation (Key Questions & Answers)

  • Q1: Why does LRU outperform FIFO on Workload A?
    Defense: "On Workload A, pages 0, 2, and 3 are repeatedly revisited. At Step 5, Page 0 hits. LRU refreshes Page 0's recency timestamp, whereas FIFO ignores hits. Consequently, when Page 3 arrives at Step 6, FIFO evicts Page 0 while LRU retains it, yielding an immediate hit for LRU at Step 7."
  • Q2: How does Figure 1 prove Belady's Anomaly?
    Defense: "A stack algorithm requires M(m, t) ⊆ M(m+1, t). On Workload D, increasing frames from 3 to 4 causes FIFO faults to jump from 9 to 10, violating inclusion. LRU's faults strictly drop from 10 to 8, proving LRU is a stack algorithm."
